## Approved contract

- Event owns catalog, retained Student membership and status-only mutation audit. UUID/code2–32/title2–160/description2–4000, startsAt<endsAt, positive integer capacity, DRAFT/OPEN/CLOSED/CANCELLED, nonnegative version/timestamps. Six boundary whitespace characters, ROOT code normalization and Unicode code-point limits. DRAFT→OPEN/CANCELLED; OPEN→CLOSED/CANCELLED; CLOSED/CANCELLED terminal. Catalog capacity cannot be reduced below actual consumed seats.
- Student self-registration/cancellation/restoration derives Student only through the JWT Identity link. ADMIN manages any Student, including profiles without accounts, and alone confirms attendance. Student-owned application projections expose only UUID/status and see current committed state despite cached entities; no foreign persistence access or locks. Owner writes re-evaluate the link after waiting for Event lock.
- Admission/restoration requires ACTIVE Student, OPEN and available capacity. User explicitly selected OPEN-only admission: dates do not silently stop admission; ADMIN closes manually. No scheduler, waitlist, fees or automatic Notification integration.
- Membership REGISTERED/CANCELLED/ATTENDED, one retained unique Student/event. User selected restoration of the same record with expectedVersion and audit history. Restoration retains UUID/creation history, records latest registeredAt and clears current cancellation time. REGISTERED/ATTENDED consume capacity; CANCELLED frees it. Attendance is terminal and allowed for ADMIN on OPEN/CLOSED. Cancellation remains allowed after closure/cancellation or Student inactivity. Event cancellation retains memberships rather than silently rewriting their history.
- Mutations lock/refresh Event then membership, check strict integer expectedVersion and count actual REGISTERED/ATTENDED under the Event lock. Catalog mutations use the same parent lock. Synchronous trusted-actor/status-only audit rolls back with business writes. Database retained unique/FKs/local shape constraints supplement supported application transaction invariants; no direct-SQL capacity guarantee.
- Six catalog and eight registration HTTP operations; bounded database page/count/filter, literal catalog search, resource-specific sort allowlists/UUID ties, safe errors and distinct Bearer OpenAPI schemas. See [Event API](../api/events.md) and [ADR 0012](../decisions/0012-event-membership-ownership-and-capacity.md).
